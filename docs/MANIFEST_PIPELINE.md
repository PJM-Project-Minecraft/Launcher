# Публикация manifest и realtime-статус

## Поток публикации

`POST /api/admin/profiles/:id/publish` больше не держит HTTP-запрос до конца
сборки. Он создаёт (или возвращает уже активное) задание и отвечает `202`:

```json
{
  "id": "uuid",
  "profileId": "uuid",
  "status": "queued",
  "phase": "waiting",
  "progress": 0,
  "logs": []
}
```

Менеджер выполняет не более одной тяжёлой публикации одновременно. Повторный
запуск одного профиля идемпотентен. Этапы: `waiting`, `scan`, `validate`,
`objects`, `unchanged` либо `bundle`, `database`, `cleanup`, `done`. Новая версия становится
видна игрокам только после успешной транзакции БД; ошибка оставляет предыдущую
публикацию рабочей.

Последнее состояние можно получить через
`GET /api/admin/profiles/:id/build`. Это fallback для случаев, когда proxy не
пропустил WebSocket upgrade. После полной перезагрузки WEB сначала получает
все известные задачи через `GET /api/admin/profiles/builds`, а затем подключает
WebSocket; выбранный профиль и открытая вкладка также восстанавливаются.

## Инкрементальная сборка

Для каждого файла в БД сохраняется mtime staging-файла. Если путь, размер,
исполняемый бит и mtime не изменились, прежний SHA-256 используется повторно.
Content-addressed object создаётся атомарно после проверки SHA и при повторной
публикации не перечитывается отдельно: целостность всех object bytes проверяется
во время сборки bundle, который теперь строится именно из object-store.

Если состав и хеши файлов полностью совпали с опубликованной версией, backend
обновляет только fingerprints и мгновенно возвращает готовый результат — номер
manifest не увеличивается, гигабайтный `tar.zst` не пересобирается. При реальном
изменении перечитываются для SHA только изменённые staging-файлы; полный bundle
по-прежнему создаётся заново и публикуется атомарно.

## WebSocket

JWT не передаётся в query string:

1. WEB с обычным `Authorization: Bearer ...` вызывает
   `POST /api/admin/profiles/events-ticket`.
2. Backend выдаёт случайный одноразовый билет на 30 секунд.
3. WEB открывает `wss://<backend>/api/realtime/profiles/ws?ticket=<ticket>`.

Сообщения всегда являются полными снимками состояния:

- `manifest.snapshot` — все известные задания сразу после подключения;
- `manifest.build` — актуальное состояние изменившегося задания;
- `system.event` — прежние сигналы `profiles` и `launcher-release`.

Reverse proxy обязан передавать заголовки WebSocket upgrade и не обрывать
бездействующее соединение раньше heartbeat (сервер отправляет ping раз в 20 с).

## Быстрый manifest в Launcher

`GET /api/profiles/:id/manifest` отдаёт ETag, связанный с версией файлов,
настройками профиля, наличием опубликованных артефактов и CDN-конфигурацией.
Launcher сохраняет последнее полное тело и
ETag рядом с локальным профилем. При неизменившейся версии backend отвечает
`304 Not Modified` до выборки `game_files`, сериализации и сжатия большого JSON,
а Launcher читает локальный кэш. Повреждённый или частично удалённый кэш
автоматически восстанавливается безусловным повторным запросом.
